1. Overview and objectives

The application is a mobile guide to the major tourist destinations and cultural-heritage sites of Region IV-A (CALABARZON), Philippines — Cavite, Laguna, Batangas, Rizal and Quezon. It is offered as an alternative to educational field trips: each destination is presented like a gallery exhibit (photo wall, history chapter, cultural-significance chapter) and followed by a short quiz written from the same text. Afterwards the app hands over to Google Maps for the real visit.

The presentation tone is museum-quality and educational. Because WMA 306 grades the user interface, design consistency, accessibility and complete loading / empty / error states were treated as first-class requirements.

Objectives

  • Deliver all Phase 1 (catalogue, CRUD, search, navigation, database) and Phase 2 (virtual tour, quiz, progress, authentication, maps) requirements on one codebase for Android, iOS and web.
  • Present 26 verified destinations (5 Cavite, 6 Laguna, 5 Batangas, 5 Rizal, 5 Quezon) with 78 freely licensed, credited photographs and 130 quiz questions.
  • Stay inside Expo Go so any phone can run the app from a QR code, and also ship a standalone Android APK.
  • Keep the codebase testable: data access behind repositories, logic in pure modules, every flow covered by automated checks.

3. Architecture

The app is layered so that anything touching the network, the device or React is isolated, and everything else is a pure function that Node can test.

Principles

  • Repository pattern. Screens and components never import supabase-js. Each repository is a factory taking a client (createDestinationsRepository(client)); repositories/index.ts binds them to the app client. The same factories run in Node in the live test scripts, so the exact production data code is tested against the real project.
  • Read hooks, not a global store. useAsyncData provides loading / error / success, retry, refresh and stale-response protection. After a write, notifyChanged() (DataSyncContext) refetches mounted screens. No Redux; a handful of small contexts (filters, sync, toast, identity, location, favorites, achievements, preferences, i18n).
  • Pure modules. Quiz scoring, progress statistics, badges, ratings maths, insights, certificates, the starter-quiz generator, the trip planner, geometry and the offline cache take plain data and contain no React Native imports.
  • Platform files. Foo.web.tsx twins (maps, certificate sharing) keep native-only libraries out of the web bundle.
  • Lists use summaries. List reads return DestinationSummary (no long texts); only getById() loads the full row. “Featured” is derived (lib/featured.ts), never stored.

4. Database schema

Two artefacts define the database: supabase/schema.sql (structure only, re-runnable) and data/destinations-seed.json (content). Additive changes ship as idempotent files in supabase/migrations/ (favorites, quiz source, ratings) applied by npm run db:migrate, which also guards the row counts.

TablePurpose and constraints
destinationsThe catalogue. province and category are CHECK-constrained to the five provinces and five categories. updated_at kept fresh by a trigger.
destination_imagesOrdered photos; row 0 is the cover (same URL as cover_image_url); caption stores the licence credit line.
quiz_questions / quiz_optionsFive questions per destination, four options each, exactly one correct. source is curated or auto (starter quiz for user-added destinations). Options have no order column; the app shuffles them.
quiz_attemptsOne row per finished attempt; the best score is derived.
destination_completions“Visited” marks; unique per destination and user key, making Mark as Visited idempotent.
favorites, ratingsUnique per destination and user key; ratings are upserted and constrained to 1–5.
Storage bucket destination-imagesPublic, 5 MB limit, JPEG / PNG / WebP. Dataset photos at <slug>/cover.jpg, gallery-1.jpg, gallery-2.jpg with a content-hash query string; photos picked in the app under covers/.

Seeded rows get deterministic UUIDs derived from the slug, so re-seeding never changes an id. Badges, insights and certificates need no tables: they are derived from the rows above.

6. Identity and authentication model

Progress rows carry a generic user key in the text column device_id: the Supabase auth user id when signed in, otherwise a random device UUID generated once with expo-crypto and kept in AsyncStorage. Guests and accounts share a single code path, and every progress hook includes the key in its cache key so data reloads by itself on sign-in or sign-out.

  • Authentication. Supabase email + password. The session is persisted in AsyncStorage and refreshed only while the app is in the foreground. Friendly messages come from friendlyAuthMessage().
  • Guest mode. “Continue as guest” gives every feature. The choice is remembered, so the Welcome screen is not repeated.
  • Guest → account transfer. When a guest signs up, transferProgress() re-keys visits, attempts, favorites and ratings to the new account, resolving duplicates first (the account's own rating wins on a clash).
  • Route protection. Stack.Protected with redirectTo: without a session or a guest choice only Welcome, Sign In and Sign Up are reachable.

7. Offline strategy

Offline support is graceful degradation rather than synchronisation. Every successful catalogue read, each fetched destination and its photo rows are saved (lib/offlineCache.ts, bound to AsyncStorage in lib/appCache.ts). When a read fails for lack of network the saved copy answers, and filtered Explore queries are re-run locally on the saved catalogue. Photos rely on the expo-image disk cache. An Offline — showing saved data banner with Retry appears on Home, Explore, Map and Details. Ratings, insights and the planner behave the same way (cached averages, input hidden offline). Writes are not queued and say so. Certificates and saved trip plans work fully offline.

8. Internationalisation and theming

Languages

No i18n framework: a typed dictionary per language (src/i18n/en.ts is the source of truth, 668 keys; fil.ts must match its shape or it is a type error). Components use useI18n() (t, categoryLabel, errorMessage, date, distance); plural forms and {{placeholders}} are supported. Pure modules return message keys, never English sentences. npm run i18n:check enforces identical keys / placeholders / plural shape, no empty text and no hard-coded UI strings in screens. Destination content (write-ups, quizzes) intentionally stays English, and Settings says so.

Theming

Two palettes with identical keys (theme/palettes.ts) are turned into Paper, navigation and Google-Maps themes by buildTheme(). Components build per-theme styles with makeStyles(); there are no literal colours or font sizes in screens (a sweep enforces it). Settings → Appearance offers System / Light / Dark with instant application, including status bars, the window background and the map style. Unit tests check token completeness and WCAG AA contrast for every text / icon pair in both palettes. Design constants (the tour's dark “gallery wall”, text over photos, the printed certificate) are identical in both themes by design.

9. Road routing (Field Trip Planner)

Since v1.1.1 the planner draws the route along real roads and reports real driving distance and time. Routing uses the public OSRM demo server (Open Source Routing Machine on OpenStreetMap data, no key). A production deployment would use the Google Routes API behind a server-held key; only src/lib/routing.ts would change.

PartDesign
RequestOne request per plan covering every point in order (the person's location when “Start from my location” is on, then each stop): router.project-osrm.org/route/v1/driving/<lng,lat;…>?overview=full&geometries=geojson. OSRM takes longitude first; buildOsrmUrl() builds it and is unit-tested for the order.
AnswerparseOsrmRoute() accepts only code: "Ok" with points − 1 legs: per-leg metres / seconds become km and whole minutes; the GeoJSON [lng, lat] line is decoded and thinned to ≤ 400 points (both ends kept) for drawing and storage.
WhenOn opening the plan and on every reorder, debounced 700 ms (useTripRoute), so a burst of moves makes one request. A subtle “Finding the road route…” chip sits on the map meanwhile.
CacheThe route is keyed by its ordered points (5 decimals) and saved with the plan in AsyncStorage (TripPlan.route); a session memo covers unsaved orders. A saved plan therefore reopens routed — also offline — without a request.
FallbackOffline, a 6-second timeout, a server error or a malformed answer all resolve to no route (the fetch never throws). The map then draws the straight dashed line and the totals return to the “approximate” straight-line figures with a short note. There is no error state.
DrawingNative: a react-native-maps Polyline (solid road line; dashed fallback) with the camera framed on stops and line. Web: an SVG polyline on the schematic map.
Attribution“Routing © OSRM / OpenStreetMap” under the map.

10. In-app 360° panoramas

The tour gains a 360° View step between the Gallery and Chapter I: full-bleed Google Street View inside the app, from the Maps Embed API (google.com/maps/embed/v1/streetview?key=…&location=<lat>,<lng>&radius=250&fov=90) in react-native-webview (included in Expo Go).

PartDesign
FrameThe Embed API refuses to load as a top-level page, so the WebView loads a tiny HTML page that frames it (panoramaHtml()); the web build renders the iframe directly. Exhibit-wall chrome, a pulsing shimmer while loading, a localized “Drag to look around” hint, Google's credit and an “Open in Google Maps” way out.
When the step appearsshowsPanoramaStep(): has_panorama = true → shown; false → left out, so those tours keep the original five steps; null (added in the app) → shown optimistically. Never offline, without coordinates or without the key. Details offers View in 360° (deep link to the step) for curated panoramas and Open in Google Maps (Street View app / site) for every destination.
CurationAt build time npm run panoramas:curate loads the framed embed for each dataset destination in headless Chromium. A panorama is confirmed when Google's place card is shown and the frame is not ≥ 90 % black; the result is written as has_panorama into the dataset, reaching the live database through an additive migration and a one-column sync by stable id (no reset; row counts verified unchanged). Result: 25 of 26 destinations; only Taal Volcano & Lake has no imagery within 250 m.
Uncurated placesThe app cannot read Google's cross-origin frame, so for a place added in the app it shows a gentle “No 360° imagery here yet” note with the Google Maps way out after nine seconds.
KeyEXPO_PUBLIC_MAPS_EMBED_KEY is publishable by design: API-restricted to the Maps Embed API, which is free at any volume, and bundled into the app and the web demo. It lives in .env and an EAS variable, never in git. The Android Maps SDK key is never placed in a WebView URL.

12. Security notes

Row Level Security stance

RLS is enabled on all eight tables and on the storage bucket. For this classroom project the policies are deliberately permissive (select / insert / update / delete) for both anon (guests) and authenticated users, with explicit grants; this is what allows guest progress and in-app catalogue editing without a server of our own. Policy names keep an _anon_ suffix because the verification script looks them up by name.

Production plan

  • Scope progress tables per user: using (device_id = auth.uid()::text) with check (device_id = auth.uid()::text) for authenticated.
  • Give guests Supabase anonymous sign-in (or a signed token) instead of a client-chosen key.
  • Restrict catalogue and storage writes to an editor role; keep catalogue reads public.
  • Rate-limit sign-up with a custom SMTP sender and re-enable email confirmation.

Secret handling

  • Only EXPO_PUBLIC_ variables are read by app code: the Supabase URL and the publishable key, which is designed to be public (access is governed by RLS). The secret key is never used.
  • SUPABASE_DB_URL is used only by setup and test scripts and is never imported by the app.
  • The Maps Embed key (EXPO_PUBLIC_MAPS_EMBED_KEY) is public on purpose — API-restricted to the free Maps Embed API — and is the only Google key the web-demo scan allows in the bundle.
  • The Google Maps key is read from .env / an EAS secret, is injected only into the native build, and is restricted in Google Cloud to the package name and the signing certificate's SHA-1.
  • .env is git-ignored; npm run secrets:check scans the tree and every commit for the DB password (raw and URL-encoded), secret keys, credentialed connection strings and Google keys before any push. The web-demo deploy script performs a similar scan of the bundle before publishing.
  • Photos come only from Wikimedia Commons under free licences and are credited in the app.

14. Known limitations

  • Database security is intentionally open for a classroom project (section 12); the production plan is documented, not applied.
  • A guest's progress is tied to that installation until an account is created.
  • Offline mode shows what was loaded once; writes (quizzes, visits, ratings) need a connection and are not queued.
  • Destination content is English only; the interface is bilingual.
  • 360° coverage is curated once at build time (Google may add or remove imagery later); for places added in the app the step is shown optimistically. Some panoramas are user-contributed photospheres near, not at, the site.
  • Road routing uses the public OSRM demo server, which has no uptime guarantee; the straight-line fallback covers outages.
  • The web demo is a convenience build: the map is a schematic stand-in (the road route is drawn on it), the 360° view depends on the browser allowing Google's iframe, haptics do nothing, narration depends on the browser's voices, and the certificate shares as text.
  • Release APKs are sideloaded builds, not a Google Play release.
  • Row-level security, the starter-quiz generator's pedagogy and the planner's fallback travel time (straight-line distance × a road factor ÷ an assumed speed, used only when road routing is unavailable) are approximations suited to the project's scope.
